> **과거 학습 기록 — 현재 실행 가이드가 아닙니다.**
> 현재 OAuth2 최소 구성은 [문서 목차](README.md)에서 확인합니다. 이 문서의 금융·ITSM·DB·이전 인증 설정, 주소, 역할 이름과 캡처는 작성 당시의 자료입니다.
> 본문의 “현재”·“최신”도 당시 시점을 뜻합니다. 과거 검사 개수를 이번 검증으로 합산하지 않습니다. 현재 실행 코드는 두 저장소의 `oauth-lab/`이며 USER·ADMIN API 모두 API7을 경유합니다.

# [과거 기록] 08. 실제 로그인부터 두 백엔드와 모의 이체까지 검증하기

> 과거 구성 기록입니다. 2026-10-06부터 FinLab Gateway는 API7 Enterprise(18090) 하나입니다. 현재 설정·실행 방법은 [Enterprise 보고서](15-api7-enterprise-integration.md)를 참고하세요. 아래 과거 실행 결과와 이미지는 당시 상태로 보존합니다.

이 문서는 **개별 코드의 테스트와 실제 서버를 연결한 검증을 구분해서** 기록합니다. 확인일은 2026-09-29입니다.

Keycloak 26.7.4, Apache APISIX 3.18.0, FinAccess, FinAdmin을 Docker로 각각 실행하고 실제 액세스 토큰으로 요청했습니다. 결과는 **HTTP 상태 코드 46개 검사 통과와 이체 후 DB 잔액 확인 성공**입니다. Java 테스트는 FinAccess 149개, FinAdmin 19개가 통과했습니다.

## 1. 어떤 경로를 검사했는가

| 경로 | 주소 | 확인하려는 내용 |
| --- | --- | --- |
| Gateway → FinAccess | `http://localhost:18090/access/...` | APISIX가 검사하고 토큰을 FinAccess로 전달하는가 |
| Gateway → FinAdmin | `http://localhost:18090/admin/...` | APISIX가 검사하고 관리자 API로 전달하는가 |
| FinAccess 직접 호출 | `http://localhost:18082/...` | Gateway 없이도 백엔드 스스로 토큰을 거절하는가 |
| FinAdmin 직접 호출 | `http://localhost:18083/...` | Gateway 없이도 백엔드가 JWT와 역할을 검사하는가 |

직접 호출 포트는 이 독립적인 검사를 보여주기 위한 로컬 실습 경로입니다. 내 컴퓨터에서만 접속하도록 `127.0.0.1`에 연결했고 DB 호스트 포트는 열지 않았습니다.

## 2. 검증 스크립트는 어떻게 실제 토큰을 받는가

파일은 `scripts/verify.py`입니다. Python 표준 라이브러리로 Keycloak 로그인 화면과 HTTP API를 호출합니다.

1. 무작위 `state`와 PKCE `verifier`를 만듭니다.
2. verifier로 만든 S256 challenge를 포함해 Keycloak 로그인 화면을 엽니다.
3. 실습 사용자의 아이디와 비밀번호를 Keycloak의 로그인 폼에 제출합니다.
4. 돌아온 주소·state·발급자가 기대한 값인지 확인합니다.
5. Authorization Code와 원래 verifier로 액세스 토큰을 받습니다.
6. 토큰을 Authorization 헤더에 넣어 API를 호출합니다.

일반 사용자 `alice`, 결재자 `bob`, 앱 관리자 `admin`, 다른 회사 사용자 `outsider` 모두 실제로 로그인합니다. 사용자 토큰 발급은 Password Grant가 아닌 **Authorization Code + PKCE**입니다.

설정을 맞추는 준비 작업에서는 Keycloak 관리용 `admin-cli` 토큰을 일시 발급합니다. 이 관리용 흐름은 사용자 로그인과 별개이며, 관리 토큰은 데스크탑이나 결과 보고서에 저장하지 않습니다.

실제 연동 중 `basic` Client Scope가 빠지면 토큰에 역할과 대상이 있어도 `sub`가 누락될 수 있음을 확인했습니다. 현재는 로그인 Client의 기본 Scope에 `basic`을 연결하여 사용자 식별자까지 전달합니다. 각 백엔드는 식별자가 빠진 토큰을 허용하도록 검사를 완화하지 않았습니다.

## 3. JWT 검증 결과

아래 표의 “네 경로”는 두 앱 각각의 Gateway 경로와 직접 호출 경로를 의미합니다. FinAdmin은 관리자 요약, FinAccess는 내 정보 API를 대상으로 검사했습니다.

| 상황 | 확인한 결과 |
| --- | --- |
| 토큰 없이 호출 | 네 경로 모두 401 |
| 토큰 본문의 subject를 바꾸고 기존 서명을 그대로 사용 | 네 경로 모두 401 |
| Keycloak이 실제 서명했지만 사용 시작 시각 `nbf`가 미래인 토큰 | 네 경로 모두 401 |
| 정상 관리자 토큰 | 네 경로 모두 200 |
| Keycloak이 실제 서명한 토큰이 충분히 오래 전에 만료됨 | 네 경로 모두 401 |
| FinAccess만 대상인 토큰으로 FinAccess 호출 | Gateway·직접 호출 모두 200 |
| FinAccess만 대상인 토큰으로 FinAdmin 호출 | APISIX에서는 403, 직접 호출에서는 401 |

### 서명 오류와 시간 오류를 구분한 이유

토큰 글자를 임의로 고쳐 만료 시각을 바꾸면 서명부터 깨집니다. 그런 토큰이 거절되어도 시간 검사가 동작했다는 증거가 되지 않습니다.

그래서 시간 검사에는 전용 테스트 Client를 사용합니다. `finlab-expiry-test`는 수명 2초 토큰을 실제 발급하고, `finlab-not-before-test`는 미래의 `nbf`를 가진 토큰을 실제 발급합니다. 이 토큰들은 Keycloak의 정상 서명을 가지고 있으므로 시간 조건 자체의 실패를 확인할 수 있습니다.

Spring은 기본 60초의 시계 오차를 허용합니다. 스크립트는 짧은 토큰의 **만료 시각에서 65초가 지난 뒤** 다시 요청합니다. 로그인 후 무조건 65초만 기다린다는 뜻이 아니라 토큰의 실제 `exp`를 기준으로 계산합니다. APISIX의 추가 시간 검사는 이 허용 범위와 별개로 설정되어 있습니다.

### 왜 audience 오류가 401과 403으로 다른가

APISIX의 OIDC 플러그인은 대상 불일치를 403으로 반환하고, Spring JWT 검증기는 audience 검증 실패를 401로 반환합니다. 따라서 모든 토큰 오류가 어느 위치에서든 같은 상태 코드여야 한다고 검사하지 않습니다. 설정한 실제 구성 요소의 결과와 실패 지점을 함께 봅니다.

잘못된 발급자, 누락된 필수 값, 다른 Client/Realm의 역할을 잘못 인정하지 않는 사례 등은 각 백엔드의 Java 보안 테스트에서도 확인합니다. 모든 Java 테스트 사례를 실제 Keycloak 검증 스크립트가 똑같이 반복하는 것은 아닙니다.

## 4. 관리자 역할과 회사별 접근 결과

| 상황 | 실제 결과 |
| --- | --- |
| `alice`가 FinAdmin 내 정보 조회 | Gateway·직접 호출 모두 200 |
| `alice`가 관리자 요약 조회 | Gateway·직접 호출 모두 403 |
| `admin`이 관리자 요약 조회 | Gateway·직접 호출 모두 200 |
| A회사 사용자 `alice`가 A회사 조회 | Gateway·직접 호출 모두 200 |
| A회사 사용자 `alice`가 B회사 조회 | Gateway·직접 호출 모두 403 |
| B회사 사용자 `outsider`가 A회사 출금 계좌로 이체 요청 | 403 |

역할과 데이터 접근 범위를 별도로 검사합니다. `user` 역할이 있다고 모든 회사의 계좌를 사용할 수 있는 것은 아닙니다. FinAccess는 검증된 토큰의 `iss + sub`로 업무 DB 사용자를 찾고, 그 사용자의 회사와 요청 대상의 관계를 확인합니다.

FinAdmin의 관리자 응답은 `sampleData: true`, 대기 3건·완료 7건이라는 고정 샘플입니다. 이번 검증이 실제 관리자 통계 집계까지 확인한 것은 아닙니다.

## 5. 로그인 신원을 업무 처리에 실제로 사용했는가

이전처럼 요청 본문의 `requesterId`나 `actorId`를 신뢰하면 호출자가 다른 사용자 이름으로 요청할 수 있습니다. 현재 HTTP API는 그런 처리자 입력을 받지 않고 검증된 토큰으로 사용자를 정합니다.

| 검사 | 실제 결과 |
| --- | --- |
| 이체 요청 본문에 `requesterId` 추가 | 400 |
| `alice`의 토큰으로 정상 이체 요청 | 201, 기록된 requesterId는 alice의 업무 DB 사용자 ID |
| 일반 사용자가 승인 시도 | 403 |
| 승인 본문에 `actorId` 추가 | 400 |
| `bob`의 토큰으로 승인 | 200, reviewerId는 bob의 업무 DB 사용자 ID |
| `bob`의 토큰으로 실행 | 200, executedBy는 bob이며 상태는 COMPLETED |
| 완료된 이체 다시 실행 | 409 |
| 관리자가 자기가 요청한 이체를 승인 | 403 |
| 결재자가 다른 요청을 반려 | 200, 상태는 REJECTED |

**Keycloak의 sub와 업무 DB의 사용자 ID는 서로 다른 값**입니다. `CurrentAppUser`가 `iss + sub`로 사용자를 찾아 업무용 UUID를 얻습니다. 스크립트는 요청·승인·실행 응답에 기록된 사용자 ID가 이 연결과 맞는지도 확인합니다.

## 6. 실제 DB 잔액 확인

검증용 계좌를 API로 만들고 출금 계좌에 테스트 시작금 10,000원을 SQL로 준비합니다. 이 시작금 설정은 실습 준비이며 사용자 입금 API나 실제 금융 거래가 아닙니다.

그 뒤 이체 요청·승인·실행은 HTTP API를 사용합니다.

| 계좌 | 실행 전 | 1,000원 이체 후 DB 조회 |
| --- | ---: | ---: |
| 출금 계좌 | 10,000원 | 9,000원 |
| 입금 계좌 | 0원 | 1,000원 |

상태 코드가 200인지만 보는 것으로 끝내지 않고, PostgreSQL에서 잔액을 조회하여 위 결과와 일치하는지 확인했습니다. 실패 시 롤백이나 동시 실행 경합 같은 더 세밀한 거래 검사는 FinAccess의 Java 통합 테스트에 포함됩니다. 이는 대규모 트래픽 부하 시험과는 범위가 다릅니다.

## 7. 브라우저 화면도 별도로 확인했다

실제 브라우저에서 다음 흐름을 확인했습니다.

1. `http://localhost:18090/`에서 로그인 버튼으로 Keycloak에 이동합니다.
2. `alice`로 로그인해 돌아온 뒤 FinAdmin 내 정보는 200, 관리자 요약은 403을 확인합니다.
3. 로그아웃하고 `admin`으로 다시 로그인하면 관리자 요약이 200으로 바뀝니다.

화면의 API 요청도 APISIX를 거칩니다. FinAccess 내 정보의 `sub`와 FinAdmin 내 정보의 `subject`는 같은 Keycloak 사용자 식별자를 나타내며, 두 응답의 `issuer`도 비교할 수 있습니다. 필드 이름이 서로 다른 점에 주의합니다.

## 8. 어디에서 거절했는지 읽는 방법

`X-Finlab-Gateway`, `X-Finlab-Upstream` 응답 헤더는 요청 경로를 구분하는 보조 표시입니다. **이 헤더만으로 백엔드가 실제로 요청을 받았다고 증명하지 않습니다.** Gateway에서 거절한 요청에도 선택된 경로가 표시될 수 있습니다.

APISIX 접근 로그에는 최종 HTTP 상태와 `$upstream_status`를 함께 남깁니다. 실제 요청의 로그를 보면 다음을 구분할 수 있습니다.

- Gateway에서 바로 거절하여 백엔드 응답 상태가 없는 요청
- 백엔드까지 전달되어 백엔드의 200 또는 403을 받은 요청

여기에 각 백엔드의 직접 호출 결과를 함께 확인하여 두 곳의 검증이 독립적으로 동작함을 판단합니다. “Gateway를 거쳤다”는 표시 하나로 이중 검증 완료를 주장하지 않습니다. 로그에는 Authorization 헤더, 본문, 로그인 code가 포함된 쿼리 문자열을 기록하지 않도록 설정했습니다.

## 9. 재실행 방법과 데이터 변경 범위

서버들이 실행 중일 때 `finadmin` 폴더에서 다음 명령을 실행합니다.

```bash
python3 scripts/verify.py
```

성공하면 `.local/verification.json`에 실행 시각, 각 검사의 기대·실제 상태 코드, 잔액 결과를 기록합니다. 파일에는 비밀번호나 토큰을 넣지 않으며 `.local/` 자체도 Git에서 제외합니다. 완료 문구의 HTTP 검사 개수는 46개입니다. 로그인·설정·DB 확인까지 HTTP가 정확히 46번만 발생했다는 뜻은 아닙니다.

스크립트가 변경하는 대상은 다음과 같습니다.

| 대상 | 수행하는 변경 |
| --- | --- |
| Keycloak `finlab` Realm | 저장소의 `finlab-*` 공개 Client 정의와 필요한 기본 Scope 연결을 맞춥니다. |
| Compose의 `app-db` | 실습 회사·사용자 연결을 준비하고 새 계좌·모의 이체 데이터를 추가합니다. |
| 데스크탑 로컬 인증 MD | 일반 실습 사용자 액세스 토큰과 만료 시각을 갱신합니다. |
| `.local/verification.json` | 이번 실행의 검증 결과를 기록합니다. |

기존 업무 데이터를 삭제하거나 DB를 초기화하지 않습니다. 기존 `finlab-*` Client 설정을 관리 화면에서 바꿨다면 검증 실행으로 저장소 설정이 다시 적용될 수 있습니다. 실습 데이터는 실행할 때마다 추가되므로, 단순 상태 조회 명령으로 생각해서는 안 됩니다.

## 10. 확인하지 않은 운영 범위

이 결과는 로컬 HTTP·Keycloak `start-dev`·단일 실습 구성의 기능 검증입니다. 운영 HTTPS, 고가용성, 장애 복구, 대규모 부하, Istio는 이번 검증에 포함하지 않았습니다. 사용자 가입·프로비저닝 API도 없으며 실습 사용자의 DB 연결은 스크립트가 준비합니다.

공개 키 기반 JWT 검증이므로 로그아웃이나 역할 변경이 기존 토큰에 즉시 반영되는 정책까지 구현한 것은 아닙니다. 업무 적용 시에는 배포 보안, 토큰 수명·폐기, 사용자 등록 절차, 운영 관측을 별도 요구사항으로 정해야 합니다.
